# CivicEcho — Secure Anonymous Citizen Reporting System

CivicEcho is a distributed secure reporting platform that lets citizens submit civic complaints to their municipality anonymously, without sacrificing report authenticity or integrity. Built as a university security project (IST Lisbon, SIRS course), it implements a full cryptographic stack — hybrid encryption, mTLS, PKI, and a token-based rate-limiting system — across five networked components deployed in isolated VM subnets.

## Features

- **Anonymous report submission**: reports are encrypted exclusively for the target municipality — neither the network nor the centralized proxy can read their contents
- **Token-based rate limiting**: citizens receive 10 write tokens per 10-minute window, each single-use with a cryptographic expiry; the authentication server enforces a cooldown before issuing new batches
- **Hybrid encryption**: each report is encrypted with a fresh AES-256-GCM key, which is itself RSA-encrypted under the municipality's public key — combining AES efficiency with RSA key management
- **Per-session read confidentiality**: read responses are encrypted with a per-request AES session key generated by the citizen, so only the requesting client can decrypt the results
- **Mutual TLS throughout**: all inter-component connections use mTLS 1.3; citizens receive a certificate signed by the authentication server, which downstream components use to verify their legitimacy
- **Replay attack prevention**: the centralized party maintains a set of used write tokens and actively cleans up expired ones, rejecting any token seen more than once
- **Multi-municipality routing**: the centralized party routes requests to the correct municipality (Lisbon or Porto) based on location metadata in the token's AAD — without reading the report
- **Audit log**: all components write structured, timestamped entries to a shared `audit.log`, recording plaintexts before protection and ciphertexts after, enabling full traceability
- **Network-level protections**: iptables DMZ isolating the database subnet, per-IP connection caps (10 concurrent sessions), TLS handshake throttling (3/s burst 10) to resist DoS, and an included `dos_attack.py` script to demonstrate the defense

## Architecture / How It Works

The system is split across three subnets to enforce network-level isolation:

```
┌─────────────────┐    ┌──────────────────┐    ┌─────────────────┐
│ Authentication  │    │     Citizens     │    │  Centralized    │
│     Server      │◄──►│                  │◄──►│     Party       │
│  192.168.0.20   │    │    192.168.0.X   |    │ 192.168.0.10    │
└─────────────────┘    └──────────────────┘    └─────────────────┘
                                                        │
                       ┌─────────────────┐              │
                       │    Database     │              │
                       │ 192.168.2.100   │              │
                       └─────────────────┘              │
                                △                       │ 
                                │                       │
                       ┌─────────────────────┐          │
                       │ Municipalities      │◄─────────┘
                       │ Lisbon: 192.168.1.1 |
                       │ Porto:  192.168.1.2 |
                       └─────────────────────┘
```

**Components**

1. **CitizenApp** — CLI client for report creation and reading. Manages write/read tokens locally and drives the full encrypt-then-send flow.
2. **AuthenticationServer** — issues X.509 certificates (signed by its CA) and batches of signed tokens during citizen enrollment. Enforces the 10-minute cooldown for token re-issuance.
3. **CentralizedParty** — the anonymizing proxy. Accepts mTLS connections from citizens, verifies token signatures and expiry using the auth server's public key, tracks used tokens, then forwards the still-encrypted payload to the correct municipality over a second mTLS connection. It never holds a key that can decrypt report contents.
4. **MunicipalityApp** — receives forwarded payloads, decrypts the AES key with its RSA private key, decrypts the report with AES-GCM, and stores it in PostgreSQL. For reads, it encrypts the response with the citizen's per-request session key.
5. **Database** — PostgreSQL storing reports as JSON. Accessible only from municipality IPs; the centralized party subnet is explicitly blocked at the firewall.

**Create report data flow**

```
Citizen
  1. Generate fresh AES-256 key
  2. Encrypt report with AES-GCM (AAD = timestamp, location, operation, token)
  3. Encrypt AES key with municipality RSA public key
  4. Send base64-encoded JSON {ciphered, iv, aad, key} over mTLS to Centralized Party

Centralized Party
  5. Verify token signature (auth server RSA public key)
  6. Check token expiry and replay set
  7. Mark token used; forward ciphertext to municipality over separate mTLS socket

Municipality
  8. Decrypt AES key with its RSA private key
  9. Decrypt report with AES-GCM (GCM tag failure = tamper detected, reject)
 10. Sanitize fields; INSERT INTO reports (PostgreSQL)
```

**Key design decisions**

- **AAD on the token**: the report's location and operation type are bound into the GCM Additional Authenticated Data, so the centralized party can route without decrypting, and any routing-field tampering invalidates the GCM tag at the municipality.
- **Dual token types**: write tokens carry an expiration timestamp and are single-use; the read token is non-expiring (citizens need standing read access) but location-bound, preventing cross-municipality queries.
- **Session key for reads**: the citizen generates a fresh AES key per read request and encrypts it for the municipality inside the protected payload. The municipality uses that key to encrypt its response, so the centralized party sees an encrypted blob going both ways.
- **Synchronized audit log**: all components write to a shared `audit.log` using a `synchronized` file writer, capturing the full plaintext → ciphertext → decrypted lifecycle of every request.

**`ProtectDocumentLibrary`** (`utils/src/main/java/report/ProtectDocumentLibrary.java`) is the shared crypto module used by all components. It exposes `protect`, `unprotect`, `check`, `ProtectSymmetric`, `UnprotectSymmetric`, and `verifyToken` — all built on standard JCA/JCE primitives (`javax.crypto`, `java.security`).

## Getting Started

### Prerequisites

All virtual machines should run **Kali Linux 64-bit**.

- Java 21+
- Maven 3.6+
- PostgreSQL 18+
- OpenSSL
- Git

### Network Configuration

Configure three host-only networks in `/Library/Preferences/VMware Fusion/networking`:

```
answer VNET_2_HOSTONLY_NETMASK 255.255.255.0
answer VNET_2_HOSTONLY_SUBNET 192.168.0.0
answer VNET_3_HOSTONLY_NETMASK 255.255.255.0
answer VNET_3_HOSTONLY_SUBNET 192.168.1.0
answer VNET_4_HOSTONLY_NETMASK 255.255.255.0
answer VNET_4_HOSTONLY_SUBNET 192.168.2.0
```

Assign network adapters per machine:

| Machine             | Adapters                              |
|---------------------|---------------------------------------|
| Citizen             | vmnet2, shared (internet)             |
| Authentication Server | vmnet2, shared (internet)           |
| Centralized Party   | vmnet2, shared (internet), vmnet3     |
| Municipality        | vmnet3, shared (internet), vmnet4     |
| Database            | vmnet4, shared (internet)             |

### 1. Generate Certificates

Run once before starting any component:

```bash
./generate-fixed-certificates.sh
```

This creates TLS certificates and keys for the authentication server (acting as CA), centralized party, both municipalities, and the database server, outputting into `certificates/`.

### 2. Start Components (in order)

**Database (192.168.2.100)**
```bash
cd initScripts/
chmod +x database_setup.sh && sudo ./database_setup.sh
```

Verify:
```bash
sudo -u postgres psql -d municipality -c "SELECT * FROM reports;"
```

**Authentication Server (192.168.0.20)**
```bash
cd initScripts/
chmod +x authServer.sh && sudo ./authServer.sh
# Listening on port 8090
```

**Centralized Party (192.168.0.10)**
```bash
cd initScripts/
chmod +x centralizedParty.sh && sudo ./centralizedParty.sh
# Listening on port 8090
```

**Municipality Servers**
```bash
# Lisbon (192.168.1.1)
cd initScripts/ && chmod +x municipalityLisbon.sh && sudo ./municipalityLisbon.sh

# Porto (192.168.1.2)
cd initScripts/ && chmod +x municipalityPorto.sh && sudo ./municipalityPorto.sh
# Both listen on port 8091
```

**Citizen Machines (192.168.0.X)**
```bash
cd initScripts/ && chmod +x citizen1.sh && sudo ./citizen1.sh
# Or manually: cd citizenApp/ && mvn compile exec:java -Dexec.args="citizen1"
```

## Usage

**Running the automated demo**

The `demo.sh` script drives a full citizen session: enrolls with the authentication server, submits 10 reports to Lisbon, attempts to request more tokens (rejected by cooldown), then reads all submitted reports.

```bash
chmod +x demo.sh
./demo.sh
```

**Manual citizen session**

```bash
cd citizenApp/
mvn compile exec:java -Dexec.args="citizen1"
# CLI menu: [1] Login  [2] Create report  [3] Read reports  [4] Request tokens
```

## What I Learned / Challenges

The hardest problem was ensuring end-to-end confidentiality through the centralized party without giving it access to report contents. The solution was found by encrypting the AES key under the municipality's RSA public key, so the proxy can only see an opaque ciphertext, sounds straightforward, but it required carefully threading the AAD (location, token, operation) outside the ciphertext so the centralized party could validate and route without decrypting. Getting the GCM Additional Authenticated Data to cover exactly the right fields while still being accessible to the proxy took several design iterations.

Implementing the read flow added another layer: since reports in the database must stay confidential even from the centralized party on the response path, we introduced a per-request AES session key that the citizen embeds in the encrypted request. The municipality extracts it, encrypts the query result with it, and returns an opaque blob — so the centralized party forwards an encrypted response it cannot read. Building that full round-trip while keeping the crypto library reusable across all components (client, centralized party, municipality) was the most satisfying engineering challenge in the project.
